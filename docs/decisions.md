# Decisions

Choices a test cannot express: canonical identifiers, defaults, naming. One
row each, decided **before** code builds on them (see the workspace
`AGENTS.md`, "Spec before code"). A decided row records the decision and the
law/test it materialized into; nothing here carries a count or a status
narrative.

| D-1 | `POST /v1/config/template` can declare more than one entity in a single call (a full block may list several `unique_id`s across several entity domains sharing one trigger). Does the create response report one collapsed boolean, or per-entity truth? | DECIDED 2026-08-01: **per entity, never collapsed.** `entities` is an array of `{unique_id, domain, entity_id, created}`, one row per entity the create declared; `unique_id` (the first entity's) stays for backward compatibility. INVARIANTS.md C-13 found Home Assistant drops a whole top-level block together when one entry in it fails validation, so every entity from one create is *expected* to agree today — but the response does not assert that as fact: a collapsed boolean would be an unverified claim about HA's atomicity baked into the wire contract, and the per-entity shape stays honest even if a future HA (or an edge case not yet found) disagrees between two entities from the same create. No separate top-level "all succeeded" convenience field either, so there is only one place a caller can read the answer from. | `_verify_created_entities` + `_CREATED_TEMPLATE_SCHEMA`/`_TEMPLATE_ENTITIES_DESC` (`src/companion/routes/templates.py`, `src/companion/openapi.py`); `tests/test_templates.py::test_create_template_block_reports_every_declared_entity`, `::test_create_template_block_partial_confirmation_is_reported_per_entity` (the mixed case, seeded so one entity resolves and the sibling deliberately does not) |
| D-2 | What does "the entity was created" mean when its live state is `unavailable`? `tests/integration/test_live.py::_entity_is_live` (built for a different question — "is this automation currently loaded after a restart") already treats *any* `unavailable` state as not-loaded, ghost or not, because an automation has no legitimate reason to be transiently unavailable. A template/script/helper entity does: e.g. a template sensor referencing another entity that has not reported yet. Copying that check verbatim into the new post-create poll would read a freshly-created, working template entity as "not created" whenever its own value has not resolved yet. | DECIDED 2026-08-01: **narrower than `_entity_is_live` — exclude a state only when it is BOTH `unavailable` AND carries `attributes.restored: true`** (a genuine leftover ghost from an earlier, unrelated delete), not `unavailable` alone. `core_api.is_live_state` answers "did the create register a real, HA-owned entity" (a ghost's registry row predates this create and proves nothing about it); `_entity_is_live` answers "is this specific entity's own function currently active" (where `unavailable` alone already means no). Same wire shape, deliberately different predicate for a different question — recorded so a future pass does not "harmonise" the two into one and reintroduce false negatives on a legitimately-unavailable-but-real template sensor. | `core_api.is_live_state` (`src/companion/core_api.py`), used by `poll_for_entity` (helper, script) and `_poll_template_entity` (template); `tests/test_core_api.py::test_is_live_state_excludes_restored_ghost`, `::test_is_live_state_bare_unavailable_without_restored_flag_still_counts_as_created` (the two poles, named against each other) |
| D-3 | How does the post-create verification find a template entity's entity_id, given it cannot be predicted from `unique_id` (D-1's premise)? The obvious candidate is the entity registry (`.storage/core.entity_registry`) — this service already reads it for storage-backed helpers (`companion/registry.py`) — keyed by `(platform=template, unique_id)`, which the first implementation used. It passed every unit test (a synchronous fixture write) and then failed against real HA in `make test-int`. | DECIDED 2026-08-01, after a live Docker reproduction: **match against live states (`GET /api/states`), never the on-disk entity registry, for a just-written entity.** Measured directly: a template entity created via `POST /v1/config/template` answered `/api/states` correctly within about a second, while `.storage/core.entity_registry`'s mtime on disk lagged the same entity's live state by roughly ten seconds (HA debounces the registry save) — ten times past any reasonable request-scoped poll budget, and an order of magnitude past what every other create route's poll already budgets (`attempts=5, delay=0.4`, ~2s). Reading the registry inside this poll therefore reported a real, live, answering entity as "not created" on every ordinary run, not just a slow one — confirmed live-fire, not theorized. The registry stays the right tool for `helper ls`'s storage-backed listing (`registry.entity_ids_by_unique_id`), which reads on its own schedule and is not racing its own just-finished write. The replacement match key is `(domain, attributes.friendly_name)` — the same "poll `get_states()`, match a criterion, take the entity_id" shape `automations.py`'s `_poll_automation_entity_id` already uses (a template state carries no analogue of an automation's `attributes.id`, so `name` — verified live, twice, to equal `friendly_name` verbatim for an unrenamed entity — is the closest available key); two states sharing that name is treated as unresolvable rather than guessed between, and a Jinja-templated (non-literal) `name:` is a known, documented limitation rather than a guess. | `_poll_template_entity` (`src/companion/routes/templates.py`); `companion/registry.py`'s module docstring records the ~10s measurement and why it disqualifies the registry for this specific caller; `tests/integration/test_live.py::TestTemplatesCRUD::test_create_template_reports_the_entity_registry_resolved` (the reproduction — first failed the exact way described here against real HA, red before the fix); `tests/test_templates.py::test_create_template_entity_confirmed_via_live_state`, `::test_create_template_entity_ambiguous_name_is_not_confirmed` |
| D-4 | `POST /v1/ref/replace` now rewrites each matching scalar in place and re-serializes a file whole only when that splice cannot be verified (#88). The single-entry write routes tell a caller about a fallback with a top-level `reformatted: true`. A replace touches several files, and the splice succeeds or falls back per file. Where does the field go, and what does a dry run say? | DECIDED 2026-10-30: **on each `changes[]` item, `reformatted: true` when that item's file was (or, in a dry run, would be) re-serialized whole, and absent otherwise.** The same name and the same "present only when it matters" shape as the single-entry routes, so a caller reads one meaning everywhere. It is per change because `changes[]` is where the per-file answer already lives (every item carries `location`), so all items of one file agree. A top-level list of locations was rejected because it would give the name `reformatted` a second type. The dry run computes the same splice and verification as the apply (both are deterministic over the file's bytes), so the preview tells the caller what the confirmed run will do. Without that, a caller could only find out after the write. | `_REF_REPLACE_SCHEMA`/`_REF_REFORMATTED_DESC` (`src/companion/openapi.py`), `refscan.replace_yaml_literal` + `surgical.splice_leaves`; `tests/test_refscan_splice.py`, `tests/test_spec_conformance.py` (`ref replace` probe `split-token`), `tests/test_invariants.py::test_single_entry_write_leaves_every_other_byte_alone` (now sweeps `ref replace`) |
| D-5 | `GET /v1/ref/grep` (hactl #115; hactl D-48..D-50 decide the surface, the matching rule and the scope) has to fix a wire shape the hactl half builds on, and say what happens to a regex that Python's backtracking `re` cannot finish. Which fields, which are always present, and is a runaway pattern a 4xx, a 5xx or a hang? | DECIDED 2026-10-30: **hits mirror `ref scan` (`location`, `path`, `matched_value`) plus `key` (the last mapping key on the path, the `/v1/ref/entities` meaning) and `kind` (`key` \| `value`); `matched_value` is the whole matching string, not the term.** `total`, `truncated` and `sources` (per-file `key_hits`/`value_hits`, counted before the 1,000-row cap) are always present, so a capped answer is stated rather than implied; `skipped` keeps the shared absent-unless-partial rule. A regex is Python `re`, case-insensitive through the `re.IGNORECASE` flag, so the pattern compiled is exactly the pattern sent and a parser message quotes the caller's own text, matched against the leaf as parsed. A pattern that does not compile (`re.error`, and the `OverflowError`/`RecursionError` `re` raises for a huge repeat count or deep nesting), or that Python warns will change meaning, is a 400 with the parser's text. A literal is lowercased one code point at a time by the simple Unicode mapping (`str.translate` over per-code-point `str.lower()`, with `U+0130` → `i`), which is Go's `strings.ToLower` exactly on Python 3.12 / Unicode 15.0.0 (measured over every code point against Go 1.26); whole-string `str.lower()` was refused because its SpecialCasing (`İ` → `i̇`) and final-sigma rule made `istanbul` miss `İstanbul` and `οδοσ` miss `ΟΔΟΣ` while `re.IGNORECASE` and the Go half found them. A pattern is evaluated in a child interpreter and killed after `REGEX_DEADLINE_S` (5 s), answered as a 400 naming catastrophic backtracking. Not a 5xx, because hactl retries a GET on any 5xx and the same pattern overruns again. Not in-process, because `([a-z]+ ?)+$` was measured at 2.6 s on 24 characters, doubling per character, and the companion serves every route from one event loop. | `_REF_GREP_SCHEMA`/`_REF_GREP_DESC` (`src/companion/openapi.py`), `companion/refgrep.py` (`HIT_CAP`, `MIN_LITERAL_LEN`, `REGEX_DEADLINE_S`, `regex_matches`); `tests/test_refgrep.py` (`::test_a_backtracking_pattern_is_cut_off_not_left_to_hang`, `::test_literal_uses_the_simple_mapping_and_agrees_with_regex`, `::test_simple_lower_is_per_code_point_and_one_to_one`, `::test_invalid_regex_is_400_with_the_parser_message`, `::test_cap_is_stated_and_counts_stay_exact`, `::test_a_pattern_python_warns_about_is_refused`), `tests/integration/test_refgrep.py` |
